# Open defects

## Mermaid labels missing inside markdown fences

A ` ```mermaid ` fence inside a `markdown` artifact renders shapes and edges
with no text labels. A standalone `.mmd` artifact renders labels correctly in
the same gallery, same frame, same renderer module.

Structure is correct and every verdict passes: the gallery reports
`nodes 6 · errors 0`, verdict `ok`. Only the label text is absent, so no
existing gate can see it.

### Refuted — do not re-test

| #   | Hypothesis                                                     | Evidence against                                                                                                                                                                                                                                                                  |
| --- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Render captured mid-flight, before labels are inserted         | `<text>` count 0 immediately AND 0 after 500 ms                                                                                                                                                                                                                                   |
| 2   | `htmlLabels` effectively true, `<foreignObject>` then stripped | `foreignObjectCount: 0`; `mermaid.initialize()` sets `htmlLabels:false` at root, flowchart, and class level (`mermaid.ts:47-53`) and both paths call the same `ensureMermaidInitialized()`                                                                                        |
| 3   | The SVG sanitizer removes `<text>`                             | `sanitizeSvgDocument` strips by denylist (`STRIPPED_TAGS`, `svg.ts:39-53`); `text` is not a member                                                                                                                                                                                |
| 4   | The scratch host is detached, so mermaid cannot measure text   | Attaching the scratch to the live `ownerDocument.body` changed nothing. `renderMermaidInto` calls `mermaid.render()` _before_ `importSanitizedSvgText` appends to the container, so the container cannot affect measurement — mermaid measures inside its own `d<id>` sandbox div |
| 5   | The markdown round-trip mangles the fence source               | `marked.parse` escapes to `&quot;` entities and `code.textContent` decodes them back; the fence is byte-identical after decode and the `%%{init:...}%%` directive survives. The standalone templates carry the same directive                                                     |

### Where the evidence points

Both paths call the same `renderMermaidInto`, so `mermaid.render()` should
return the same SVG string for each. The only steps the markdown path performs
that the standalone path does not are in `markdown.ts:69-81`:

```ts
const scratch = document.createElement("div");
await renderMermaidInto!(scratch, source);
const svg = scratch.firstElementChild;
if (svg !== null) pre.replaceWith(svg);   // ← moves the SVG into template.content
...
ctx.container.appendChild(template.content);
```

`template.content` belongs to a separate inert document, so `replaceWith`
adopts the SVG across documents. That step is untested and is the leading
suspect.

### The measurement that settles it

Count `<text>` at four points for the same diagram, with a standalone `.mmd`
artifact as the control at every point:

- **A** — the raw `result.svg` string from `mermaid.render()` (`mermaid.ts:70`)
- **B** — `scratch` after `renderMermaidInto` resolves
- **C** — the SVG after `pre.replaceWith(svg)`, inside `template.content`
- **D** — the live container after `appendChild(template.content)`

The first stage where markdown reads 0 while standalone does not is the answer.

Drive it through the passing live-gallery harness (`tests/helpers/gallery-live.ts`,
used by `gallery-geometry.test.ts`) rather than a fresh probe file — two
bespoke probes have failed at `gallery shell navigation timed out` while that
harness passes. Stamping the counts onto the renderer root as `data-*`
attributes lets the existing isolated-world read pick them up.

Editing renderer source requires `bun run build` **and** a service restart:
`/gallery/frame` is generated by an imported module, so a running service keeps
serving its boot-time code.

### When it is fixed

Gate it on label text content — `source bytes`, `hash + store`, `validate` —
in a new acceptance file registered in the `acceptance-tier1` matrix. A count
or status assertion proves nothing: the broken render already reports
`nodes 6 · errors 0 · ok`.
